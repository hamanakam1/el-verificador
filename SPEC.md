## System Role

**The Autonomous Gatekeeper for the Taskrivet Pipeline**

**Pipeline Position:** Downstream from Taskrivet; upstream from EdgeRecord.

El Verificador is the gate between "code written" and "code committed".
Taskrivet cannot grade its own homework. El Verificador independently audits
Taskrivet's work inside the hydrated Docker sandbox before the sandbox is torn
down and code is merged.

---

## Objective

Verify that a `DistilledWorkPackage` produced by El Destilador was faithfully
implemented by Taskrivet, that all acceptance checks pass, and that the result
is safe to commit. Every verification decision is immutably logged to EdgeRecord.

---

## Core Mechanisms

### 1. Independent Acceptance Testing

El Verificador provisions the Docker sandbox hydrated by El Hidratador and runs
the acceptance pipeline inside it:

1. Unit tests (`pytest -q`)
2. Lint (`ruff check .`)
3. Security scan (`bandit -r . -q`)

Only a container exit code of `0` for every check counts. Taskrivet's
self-reported status is never trusted.

### 2. Intent Alignment (The Semantic Diff)

Passing tests are not enough — the code must solve the user's original problem.
El Verificador compares the actual AST changes and git diff against the
`DistilledWorkPackage` originally generated by El Destilador:

- Did the agent build the API route, or just write `# TODO: Implement route`?
- Are changed files covered by the work package's `related_files`?
- Do goal keywords appear as code identifiers?

The diff is computed from the real source, not from a symbol name:

- A symbol that was **rewritten** is reported as `MODIFIED`, with the old and
  new source. Comparing symbol names alone cannot see a changed function body.
- A **stub** is a function, method, or class whose whole body is `pass`, `...`,
  or `raise NotImplementedError`. A `TODO`/`FIXME` counts only when it is a
  real comment — the word "bypass" is not a `pass` statement, and a TODO inside
  a string literal is not a TODO.
- The **coverage score** is the weighted combination of the declared scope
  that was touched and the goal's checkable claims that the changed code
  provides. The checkable claims are the **identifiers the goal names** —
  `register_user`, `validate_payload`, `app/routes/users.py`. Prose is not a
  claim anyone can check against code, and counting it would make the score
  depend on how the goal happened to be worded. A goal that names no
  identifiers falls back to its significant words, and the basis says which
  was used. The score is reported with its inputs: the goal words, the ones
  that were covered, the ones that were not, the identifiers the goal named,
  and the related files that were touched. A score with no inputs cannot be
  audited.

Verification fails when:

- a stub or a TODO comment is found (`fail_on_todo_stubs`, default on);
- nothing changed at all; or
- the goal names identifiers and the change provides **none** of them. A
  change that contains none of the things the goal asked for is not an
  attempt at the goal, however green the acceptance commands are.

The configured `intent_coverage_threshold` is **reported, not yet a gate**:
turning it into one before the score is calibrated against a population of
real work packages would fail correct implementations that spell a name
differently. The decision model that replaces it is specified in `ROADMAP.md`
(Phase 2, the obligation model).

### 3. The Guardrailed Feedback Loop

If Taskrivet breaks the build or the intent check, El Verificador does not
blindly say "try again". It acts as a precise debugger:

- Captures the exact stack trace, the specific semantic diff, and the failed
  test output
- Packages this into a bounded, strict "Correction Prompt"
- Hands the prompt back to Taskrivet for a retry
- **Crucially:** Enforces a strict iteration limit (`max_retries=3`). If
  Taskrivet fails three times, the loop is broken, the container is paused,
  and the ticket is flagged on the Ticket Board for human intervention

### 4. State Commit & Teardown

When the code passes both machine tests and the semantic intent check:

1. Commits the code to the target Git branch
2. Tears down the Docker containers and releases compute resources
3. Fires a cryptographically secure payload to EdgeRecord, immutably logging
   what was changed, why it was changed, and proof that it passed

**The commit path stages only what was reviewed.** There is no blanket add.
A verifier that runs `git add -A` on a shared checkout will eventually
commit somebody's untracked secrets, their build artefacts, and another
session's work — and the commit will look like a success. The set of paths
to stage is therefore explicit, and the commit is refused when:

- the index already holds staged work that the verification did not review;
- the working tree's copy of a reviewed file differs from the commit the
  verification actually inspected, because committing it would put
  unverified bytes into a commit that carries a verification receipt.

When the reviewed paths are already committed there is nothing to do, and
the outcome is recorded as `already-committed` rather than as a commit the
verifier made. `VerificationResult.commit_note` always says what happened,
and the audit record carries it.

### 5. The Taskrivet Ledger Integration

A Correction Prompt that is only printed for a human is not a feedback loop.
The `TaskrivetAdapter` closes the loop through Taskrivet's own coordination
ledger, so every verification outcome is a first-class lifecycle event that
Taskrivet (and therefore the operator) can see.

The adapter drives Taskrivet's JSON CLI (`python -m taskrivet`) rather than
reimplementing its rules, so ownership, lease, scope-conflict, and token-budget
rules stay authoritative in one place.

| Verification event | Taskrivet commands | Effect on the ledger |
|---|---|---|
| Work begins | `task-add`, `start` | The task is seeded from the work package's acceptance contract and scope, then a session is opened under the verifier's owner |
| An attempt fails | `fail`, `context-add`, `retry`, `start` | The failure is fingerprinted, the bounded Correction Prompt is attached as task context, the task returns to `ready`, and a fresh session owns the next attempt |
| An attempt passes | `checkpoint`, `finish`, `accept` | Usage and evidence are recorded, the session closes, and the task is accepted |
| The budget is exhausted | `fail` | The final failure is recorded so the task is **blocked** for human intervention instead of being left running with an abandoned session |

Details that matter:

- A failure always has an **owning session**. If no session is open, one is
  opened rather than dropping the failure record silently.
- The Correction Prompt is attached as **bounded context**, not pasted into an
  unbounded field. Summaries, reasons, and evidence are length-capped.
- The integration is **inert unless configured**: without both
  `--taskrivet-db` and `--taskrivet-task` the CLI behaves exactly as before
  and prints the prompt for the operator.
- The adapter reads the work-package schema **defensively**. The schema
  evolves, and a verifier that crashes on an older or newer schema would
  report a broken gate rather than a broken build.

## Data Contracts

All contracts are pydantic v2 models (`extra="forbid"`):

| Model | Purpose |
|-------|---------|
| `IntentPackage` | Lightweight view of a `DistilledWorkPackage` consumed by the verifier |
| `CheckResult` | Result of one acceptance check (exit code, stdout, stderr) |
| `SemanticDiff` | AST/git diff vs. distilled intent; coverage score with its goal words, covered words, uncovered words, and touched related files |
| `CorrectionPrompt` | Bounded prompt handed back to Taskrivet on failure, plus the optional advisory note composed by the local model |
| `VerificationResult` | Complete result of one verification run |
| `VerificationAudit` | Immutable EdgeRecord audit record (SHA256 hash + hash chain) |

Non-contract integration surface:

| Component | Purpose |
|-------|---------|
| `TaskrivetAdapter` | Drives Taskrivet's JSON CLI to record verification outcomes in its coordination ledger (§5) |

## EdgeRecord Audit

Every verification decision is written to the EdgeRecord SQLite ledger (WAL
mode) at `~/.edgerecord/ledger.sqlite`:

- Content hash = SHA256 over the canonical JSON of the whole decision — the
  work package, the repository, the decision, the rationale, **the key
  evidence**, the attempt count, the timing, and the timestamp. The digest
  covers the evidence, not only the sentence that describes it.
- `previous_audit_hash` chains records for tamper evidence, in the order they
  were written rather than the order of their timestamps.
- `verify_chain()` validates the chain **and re-hashes every record**: a
  record whose contents were edited after it was written no longer matches
  its stored digest, and the chain reports which record broke and why.
- One definition of the hash. The model computes it, the writer stores it,
  and the verifier recomputes it from the same canonical form.

## Guardrails

| Guardrail | Value |
|-----------|-------|
| `max_retries` | 3 (hard iteration limit) |
| Intent coverage threshold | 0.85 — reported with its inputs; a gate once the score is calibrated (see §2) |
| Fail on TODO stubs | enabled — honours `fail_on_todo_stubs`; a stub or a TODO comment fails the run |
| Dry-run mode | available for offline development |
| Local-first | no cloud dependencies; Ollama Qwen at `http://127.0.0.1:11434` |

## Failure & Escalation

| Outcome | Action |
|---------|--------|
| `PASS` | Commit code, teardown sandbox, log to EdgeRecord; checkpoint, finish, and accept the Taskrivet task |
| `FAIL` | Issue Correction Prompt to Taskrivet (counts toward `max_retries`); record the failure, attach the prompt as context, and requeue the task |
| `ESCALATE` | `max_retries` exhausted; pause container, flag ticket for human; record the final failure so the Taskrivet task is blocked for a human rather than left running — **with the failing checks and the semantic diff attached**, because that is the evidence the human needs |

## CLI

```
python -m el_verificador verify  --work-package wp.json --repo . --base HEAD~1 --head HEAD --dry-run
python -m el_verificador audit   --work-package dwp-abc --verify-chain
python -m el_verificador config  --init
```

With the Taskrivet ledger integration enabled:

```
python -m el_verificador verify \
  --work-package wp.json --repo . --base HEAD~1 --head HEAD \
  --taskrivet-db ~/.taskrivet/ledger.sqlite \
  --taskrivet-task my-task-id \
  --taskrivet-scope repo/api
```

| Flag | Meaning |
|------|---------|
| `--taskrivet-db` | Path to the Taskrivet ledger. Required to enable the integration |
| `--taskrivet-task` | Taskrivet task id that records this verification. Required to enable the integration |
| `--taskrivet-owner` | Owner recorded on the Taskrivet session (default `el-verificador`) |
| `--taskrivet-scope` | Resource key for conflict detection (repeatable) |
